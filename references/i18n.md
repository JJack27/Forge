# Internationalization (i18n)

The book supports multiple languages via **one site with a runtime language switcher**. UI strings and all chapter/test content live in per-language JSON files; switching language re-fetches the right files and re-renders without a page reload.

Per the learner's choices at Stage 0.5: the book is built end-to-end in the **primary language first** (the language they're chatting in), delivered, and only then translated into the other selected languages as a follow-up step (Stage 4.5).

## The i18n invariant

**The set of keys is identical across every `locales/<lang>.json`, and every `content/<lang>/` folder mirrors the same chapter structure.** If a key or chapter exists in `en`, an equivalent must exist in `zh`, `es`, etc. This is what makes the runtime switcher work: it just swaps files; it never has to add or remove UI elements.

Concretely:

- `locales/en.json` and `locales/zh.json` have the **same keys** with **translated values**.
- `content/en/meta.json` and `content/zh/meta.json` have the **same chapter list** (same `id`, `chapter`, `file` names) with **translated titles**.
- `content/en/ch-03.json` and `content/zh/ch-03.json` have the **same structure** (same number of questions, same `type`, same `correct`/`accepted`/`keyPoints` shape) with **translated prose**, and crucially the **same anchors**.

## Anchors are language-neutral

A test's `review` field is a section id like `sec-ownership-rules`. This id must be **identical across languages** — only the prose inside that `<section>` changes. This guarantees that a review link works no matter what language the learner is reading in, and that the same scoring/feedback code works without per-language logic.

Convention: anchors are kebab-case, English-derived slugs, stable. `sec-borrow-checker-rules`, `sec-request-lifecycle`, `ch-3`. Do not translate them.

## What gets translated, what doesn't

| Translate | Do NOT translate |
|---|---|
| UI strings (`ui.*` keys) | Keys themselves (`ui.submit`) |
| Chapter titles, objectives | Chapter `id`, `chapter` number |
| `bodyHtml` prose | `<section id="...">` anchors; **code blocks** inside the prose |
| `pitfallsHtml` prose | Filenames, file paths, line numbers |
| Question `prompt`/`promptHtml` prose | Code inside the prompt |
| `options[].label` prose | `options[].value` (these are scoring tokens) |
| `answer`, `rationale` prose | — |
| `keyPoints` prose | The fact that there are N key points (keep the count) |
| `placeholders` (fill hints) | `accepted` answers (unless the answer is itself a natural-language word — then translate the *acceptable* forms too) |
| `viz[].caption` (if it's prose) | `viz[].code`, `viz[].slug`, `viz[].type` |
| Interactive `prompt`/`answer`/`rationale` | Interactive `code` and `check` |

**Special case — `accepted` for fill questions:** if the answer is a code symbol or API name (`Vec::push`, `useState`), do **not** translate it — it's the same in every language. If the answer is a natural-language term ("ownership"), translate the acceptable forms so the learner can type the term in their language.

**Special case — `correct` for mcq:** the `value` tokens are scoring tokens, not display. Keep them identical across languages (`"a"`, `"b"`, `"c"`). Only the `label` prose is translated.

## Visualizations and the i18n invariant

Vizs are code-as-data, so they follow a strict rule: **the `code` and `check` strings are identical across languages. Only `caption` and any label text the viz shows through `helpers.t()` change.**

Concretely, when translating a chapter that has vizs:

- Copy the entire `viz[]` array across unchanged — same `code`, same `slug`, same `type`.
- Translate only the `caption` (if it's prose; if it's a locale key, leave the key and translate its value in `locales/<lang>.json`).
- If the viz shows labels via `helpers.t("viz.something")`, add `viz.something` to each locale file with the translated value. The `code` keeps calling `helpers.t("viz.something")` — the lookup resolves to the right language at render time.
- For interactive questions, the `code` and `check` are copied verbatim. Only the `prompt`, `answer`, and `rationale` get translated.

Why this works: viz code reads labels through `helpers.t()` at render time, so the same compiled function localizes automatically when the language switches. The code never needs to know what language it's rendering for.

Why it matters: if you "translate" the viz code (e.g., changing variable names, restructuring the SVG), the two languages will drift — a viz that works in English may break in Chinese. Keep viz code byte-for-byte identical across languages.

## Test logic is language-neutral

The scoring code (`js/scoring.js`) operates on `data-*` attributes and is identical for every language. You must keep the **structure** of each test identical across languages:

- Same number of questions per chapter.
- Same question types in the same order.
- Same `correct`/`accepted` sets (modulo the natural-language-term exception above).
- Same `keyPoints` count.

If you change the test when translating, you've broken the invariant and the languages will diverge.

## localStorage namespacing

Scores are stored per language: `book:<slug>:<lang>:ch:<n>`. A learner who passes the English chapter 3 test but hasn't taken the Chinese one will see English chapter 3 as ✓ and Chinese chapter 3 as ○. This is intentional — passing a test in one language doesn't certify you in another.

## The language switcher

Rendered by `main.js` at the bottom of the TOC as a `<select>`. The list of supported languages comes from `BookI18n.getSupported()` (hardcoded in `js/i18n.js` — extend `SUPPORTED` when you add a locale). On change, `main.js` re-inits the locale and re-fetches content for the new language.

## Translation workflow (Stage 4.5)

For each additional selected language, after the primary-language book is approved:

1. Copy `locales/<primary>.json` → `locales/<newlang>.json`, translate the values, keep the keys.
2. Copy `content/<primary>/` → `content/<newlang>/`.
3. For each chapter file: translate `title`, `objectives`, `bodyHtml`, `pitfallsHtml`, and every question's prose. **Do not touch** `id`, `chapter`, anchors, `type`, `correct`, `value`s, question counts, or (for code-symbol answers) `accepted`.
4. Translate the chapter `title` in `meta.json` (keep `id`/`chapter`/`file`).
5. Verify the invariant: same keys, same structure, same anchors, same test logic. (See "Verifying the project" in `project-structure.md`.)
6. Add the new language to `SUPPORTED` in `js/i18n.js`.
7. Deliver the language and ask whether to continue to the next.

## Translation tips

- **Preserve code blocks verbatim.** A Rust snippet is the same in English and Chinese. Only translate comments inside code if they're prose-y and would otherwise confuse; often it's clearer to leave them.
- **Don't translate proper nouns, project names, or API names.** "PostgreSQL", "React", `useState`, "Borrow checker" (often left untranslated in Chinese tech writing).
- **Keep markup identical.** If `bodyHtml` has `<p>...</p><section id="sec-x"><h3>...</h3></section>`, the translated version has the same tags and the same id, just different text inside.
- **Translate meaning, not words.** A scenario question about "the borrow checker rejecting this code" should become a natural scenario question in the target language, not a word-by-word gloss.
- **Keep the test difficulty identical.** If the English version of a question is tricky, the translated version should be equally tricky — don't accidentally make it easier or harder by simplifying the wording.
